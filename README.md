### 1️⃣ [UI automation card transfer tests with Selenide](https://github.com/Meruduya/UI-automation-card-transfer-tests-with-Selenide)

**Stack:** `Java` · `JUnit 5` · `Gradle` · `Selenide` · `Lombok` · `GitHub Actions`

#### 🎯 *Задача*

Автоматизировать тестирование банковского приложения, в котором пользователь может переводить денежные средства между своими картами. Нужно было проверить как **успешные переводы**, так и ситуации, когда **сумма перевода некорректна**.

#### ✅ *Что реализовано*

- авторизация пользователя и переход в личный кабинет;
- успешный перевод **в обе стороны**: с первой карты на вторую и со второй на первую;
- проверка балансов обеих карт после перевода;
- негативный сценарий: перевод суммы, **превышающей баланс**, с проверкой текста сообщения об ошибке;
- проверка, что после неуспешного перевода **балансы карт не изменились**;
- сценарий перевода **суммы 0** с проверкой, что балансы остались прежними.

#### ⚙️ *Реализация*

Тестовый код организован по паттерну **Page Object**: отдельные классы описывают страницу входа, страницу подтверждения, личный кабинет и страницу перевода, а тесты содержат только сценарии проверки. Тестовые данные вынесены в отдельный класс `DataHelper`.

Тесты запускаются в **GitHub Actions**: при каждом push приложение стартует в фоне, а тесты выполняются в *headless*-режиме браузера.

### 2️⃣ [Cypress API tests — CRUD](https://github.com/Meruduya/Cypress-API-tests-CRUD)

**Stack:** `JavaScript` · `Cypress` · `REST API` · `HTTP` · `Custom Commands`

#### 🎯 *Задача*

Автоматизировать проверку API для работы с пользовательскими данными: **создание, изменение и удаление** пользователя.

#### ✅ *Что реализовано*

- `POST`-запрос для создания пользователя;
- получение идентификатора созданного пользователя;
- `PUT`-запрос для изменения имени и фамилии пользователя;
- `DELETE`-запрос для удаления пользователя;
- проверка статуса ответа `200`;
- проверка наличия `id` и значений полей `firstName` и `surName` в JSON-ответе.

#### ⚙️ *Реализация*

API-запросы написаны средствами Cypress (`cy.request`). Для повторяющихся действий созданы собственные **Custom Commands**: создание, обновление и удаление пользователя, а также создание пользователя с получением его `id`.

Общие проверки успешного ответа и полей пользователя тоже вынесены в отдельные команды, поэтому сами тесты получились *короткими и читаемыми*.

### 3️⃣ [SQL database testing — MySQL + JDBC](https://github.com/Meruduya/SQL-database-testing-MySQL)

**Stack:** `Java` · `JUnit 5` · `Selenide` · `MySQL` · `SQL` · `JDBC` · `Apache Commons DbUtils` · `Faker` · `Lombok` · `Docker Compose` · `Page Object`

#### 🎯 *Задача*

Автоматизировать проверку авторизации в банковском приложении и связать UI-тестирование с базой данных. *Особенность задания:* код подтверждения нужно было получать **напрямую из базы данных**.

#### ✅ *Что реализовано*

- успешная авторизация существующего пользователя с кодом подтверждения из БД;
- попытка входа **несуществующего пользователя** (случайные логин и пароль) с проверкой сообщения об ошибке;
- ввод **неверного кода подтверждения** с проверкой сообщения об ошибке;
- выполнение SQL-запросов из тестового кода;
- очистка таблицы кодов после каждого теста и всех тестовых данных после завершения тестов;
- запуск MySQL со схемой базы данных через **Docker Compose**.

#### ⚙️ *Реализация*

Для работы с интерфейсом используются **Selenide** и **Page Object**. Для работы с базой данных создан отдельный класс `SQLHelper`: он подключается к MySQL через **JDBC** и выполняет запросы с помощью *Apache Commons DbUtils*. Случайные пользователи и коды подтверждения для негативных сценариев генерируются с помощью **Faker**.

> Пользователь вводит логин и пароль → тест берёт последний код подтверждения из БД → код вводится в интерфейсе → после теста данные очищаются.

### 4️⃣ [JMeter load testing](https://github.com/Meruduya/JMeter-load-testing-Cinema)

**Stack:** `Apache JMeter` · `Docker Compose` · `MySQL / MariaDB` · `CSV test data`

#### 🎯 *Задача*

Познакомиться с организацией нагрузочного тестирования в JMeter: разными **типами тестов**, **параметрами нагрузки** и **тестовыми окружениями**.

#### ✅ *Что реализовано*

- развёртывание тестового стенда (веб-приложение кинотеатра, база данных, phpMyAdmin) через **Docker Compose**;
- изучение готового шаблона JMeter-сценариев для WordPress: однопользовательский прогон (*baseline*), **load test** и **stress test**;
- собственный сценарий добавления комментария к записи блога на **100 потоков**;
- отдельные `.properties`-файлы для разных окружений (*dev, test, qa, stag*) и наборы тестовых данных в CSV.

#### ⚙️ *Реализация*

Сценарии оформлены в формате `.jmx` и разбиты на **переиспользуемые модули**: вход, главная страница, просмотр записи, поиск, RSS, комментарии, лайки. Параметры нагрузки (время разгона, длительность, интенсивность действий, доля анонимных и авторизованных пользователей) задаются через `.properties`-файлы и передаются при запуске.

### 5️⃣ [Appium Android UI tests](https://github.com/Meruduya/Appium-Android-UI-tests)

**Stack:** `Java` · `Appium Java Client` · `Selenium` · `UiAutomator2` · `JUnit 5` · `Gradle`

#### 🎯 *Задача*

Автоматизировать тестирование пользовательского интерфейса Android-приложения: проверить **основной сценарий** и поведение при **пустом вводе**.

#### ✅ *Что реализовано*

- запуск приложения на Android-эмуляторе через Appium;
- негативный сценарий: нажатие кнопки при **пустом поле ввода**, текст на экране не меняется;
- ввод текста и **переход на новый экран** (Activity);
- проверка, что на новом экране отображается введённый текст;
- ожидание появления элементов перед взаимодействием;
- закрытие драйвера после каждого теста.

#### ⚙️ *Реализация*

Тесты написаны на Java с использованием **Appium Java Client** и **JUnit 5**. Элементы ищутся по `resource-id`, а синхронизация с интерфейсом выполняется через `WebDriverWait` и `ExpectedConditions`.

Настройка драйвера и capabilities вынесена в отдельный класс `Config`, а поиск элементов экрана — в отдельный класс, так что тесты содержат *только сценарии*.

### 6️⃣ [Espresso Android UI tests](https://github.com/Meruduya/Espresso-Android-UI-tests)

**Stack:** `Java` · `Espresso` · `Espresso Intents` · `Espresso Contrib` · `JUnit 4` · `AndroidX Test` · `IdlingResource`

#### 🎯 *Задача*

Автоматизировать тестирование интерфейса Android-приложения: проверить **отображение элементов**, работу **списка** и **переходы** между экранами.

#### ✅ *Что реализовано*

- проверка текста на главном экране;
- открытие бокового меню и переход в раздел **Gallery**;
- проверка содержимого списка: наличие элемента «7» и общее количество элементов (10);
- **собственный Matcher** для подсчёта элементов `RecyclerView` и собственная проверка типа элемента;
- **проверка Intent**: пункт меню *Settings* открывает ссылку (`ACTION_VIEW` с адресом `https://google.com`);
- синхронизация тестов с приложением через **IdlingResource**.

#### ⚙️ *Реализация*

Тесты написаны на Java с использованием **Espresso** и **JUnit 4**. Для работы с боковым меню используется *Espresso Contrib*, для проверки Intent — *Espresso Intents*.

Асинхронная загрузка данных учитывается через `IdlingResource`: тест ждёт, пока приложение освободится, *вместо фиксированных пауз*.
